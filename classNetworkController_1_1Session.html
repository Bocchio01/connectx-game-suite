Detailed Description

Threads of a session:

  • worker thread: connects, then executes the queued jobs one at a time (the synchronous requests of the Client block until the answer, and the Client allows one at a time anyway); it also owns the event thread, which it starts after connecting and joins before exiting, i.e. before the Client can be destroyed;
  • event thread: runs Client::run(); all the Client callbacks are invoked there. Both only ever talk to the GUI through post(), which delivers a queued call to the controller (and does nothing once the controller has detached from the session).

How the Client behaves, and what the jobs rely on: a request returns std::nullopt when the answer does not come in time or when the connection is closed meanwhile (disconnect() releases it at once); when the server refuses it with an ERROR message it returns at once, with success == false, AFTER the error callback has run (so the code of the error, which the response does not carry, is already known).
